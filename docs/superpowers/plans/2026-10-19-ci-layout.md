# CI layout and live-demo checks (#10) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One pipeline per push; `e2e`, `demo` and `upgrade-test` automatic and blocking on `main`, on schedules and on a merge request whose paths they cover, manual otherwise; a browser check of demo.wayscribe.dev daily and after every deploy that alerts through a failed pipeline and ntfy; and a release tag that publishes on its own while `deploy-demo` stays manual.

**Architecture:** A top-level `workflow: rules` block picks the merge request pipeline while one is open and the branch pipeline otherwise. Jobs that had no `rules` (and so never ran in a merge request pipeline) gain an `every-pipeline` anchor; jobs that excluded merge requests stop doing so. The three stack jobs get per-job path lists held by `tests/ci-rules.test.ts`, which evaluates every rule the way GitLab does, including the transitive workspace dependencies of `apps/web` and `apps/api`. A read-only Playwright suite in `apps/web/e2e-live` with its own `playwright.live.config.ts` (`pnpm test:live`) checks the live demo; the `live-demo` job runs it on a schedule gated by `LIVE_DEMO_CHECK=1` (every other job skips that pipeline) and after `deploy-demo` on a tag, and `scripts/live-demo-alert.mjs` posts to ntfy from `after_script`. The release jobs lose `when: manual`, `publish-images` gains `demo-overlay` in its `needs`, and `deploy-demo` needs `publish-images` only.

**Tech Stack:** GitLab CI (gitlab.com, `glab` 1.100), the `yaml` 2.9.1 package (already a root devDependency, already used by six tests), Vitest 4, Playwright 1.63 (image `mcr.microsoft.com/playwright:v1.63.0-noble`, which carries git and curl), Node 24, ntfy.sh.

**Spec:** `docs/superpowers/specs/2026-10-19-ci-layout-design.md` (issue #10, ADR-073)

## Deviations from the spec

Each follows what GitLab and this file actually need and keeps the spec's intent. Items 3, 7, 11 and 12 change behaviour the spec describes; item 12 needs a decision from Jorge (see "Decisions for Jorge").

1. **Workflow order and the UI source.** The spec's `workflow` lists the schedule rule last and has no rule for `web`. A scheduled pipeline is a branch pipeline, so on a branch with an open merge request the spec's `$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS` rule would drop it, and a pipeline started with Run pipeline in the UI on such a branch would be dropped the same way. The schedule rule moves first and `$CI_PIPELINE_SOURCE == "web"` is added before the `never` rule. Pushes behave exactly as the spec says.
2. **Sixteen jobs had no `rules` at all**, which GitLab reads as `only: [branches, tags]`: they never ran in a merge request pipeline. Under the new `workflow` they would vanish from merge requests entirely (`format`, `lint`, `typecheck`, `helm`, `debt`, `audit`, `secrets`, `unit`, `sdk-node`, `sdk-go`, `sdk-python`, `examples-go`, `examples-otlp-collector`, `examples-otlp-java`, `database`, `build`). Each gains `<<: *every-pipeline` (`rules: [skip the live check, when: on_success]`). Three more matched only `$CI_COMMIT_BRANCH`, which a merge request pipeline does not set (`upgrade-test`, `demo-overlay`, `publish-images-rehearsal`); their rules now also match `merge_request_event`.
3. **The live-demo schedule's pipeline holds `live-demo` alone.** The spec gates `live-demo` on `LIVE_DEMO_CHECK == "1"` but says nothing about the rest of the pipeline. A schedule on `main` would otherwise run every main job every day (with this change that includes `e2e`, `demo` and `upgrade-test`, plus `container-scan`, `sbom` and three `database` jobs), for a one-minute check. Every other job's rules start with `*skip-on-live-demo-check` (`if: $LIVE_DEMO_CHECK == "1"`, `when: never`), and `tests/ci-rules.test.ts` asserts the pipeline holds exactly `live-demo`.
4. **The allow list is the jobs that never run on a feature branch**, not only the release jobs: `container-scan`, `sbom` (image builds kept to main, tags and schedules), `pages`, `mirror-to-github` and `github-release` join `release-verify`, `publish-*` and `deploy-demo`. The test asserts the property behind the spec's two allow-list assertions: every job a feature branch pipeline creates for a set of changed files is also created in the merge request pipeline for the same files, and the jobs absent from every merge request pipeline are exactly the allow list.
5. **Path lists are wider than the spec's table.** `e2e` takes `apps/api/**` (the spec says `apps/api/src/**`; the API's `package.json` and `tsconfig*.json` change what `pnpm build` produces), the root `package.json`, `pnpm-workspace.yaml` (its `overrides` change resolved dependencies) and `tsconfig.base.json`. Its workspace packages are the transitive closure over `dependencies` and `devDependencies` of `apps/web` and `apps/api`: `config`, `database`, `payload-diff`, `payload-security`, `protocol` and `sdk-node` (the API's devDependency, built by `pnpm build`). `apps/web` itself has no workspace dependency (ADR-072). `demo` adds `infrastructure/compose.yaml` (the spec's `infrastructure/compose.*.yaml` does not match it, and the job starts it), `.env.example` (the job copies it), every package its images build from (`packages/**`), the root manifests and `vitest.demo.config.ts`. `upgrade-test` adds its own script (`scripts/upgrade-test*`), `packages/payload-security/**` (the key formats `rotate:reencrypt` upgrades) and `apps/api/Dockerfile`. The test checks all three lists, not only `e2e`'s.
6. **Tags and plain branches keep their old behaviour for the stack jobs.** On a tag `e2e` and `demo` stay manual (as today; `release-verify` is the tag's acceptance gate), `upgrade-test` stays automatic on `vX.Y.Z` and absent on other tags. On a feature branch with no merge request all three are manual, which is the spec's "any other MR or branch".
7. **`live-demo` needs `deploy-demo` as optional.** A plain `needs: ["deploy-demo"]` makes every pipeline without `deploy-demo` invalid ("needs a job that is not in the pipeline"), and `deploy-demo` exists only on `vX.Y.Z` tags. `needs: [{job: deploy-demo, optional: true}]` keeps the tag ordering and lets the schedule and merge request pipelines create the job. On a merge request or feature branch `live-demo` is manual with its failure allowed (the spec asks for a manual run from the branch); on a push to `main` it does not run.
8. **The tap-target check runs at 375 px and also checks width.** At 1440 px each journey link is a table row no taller than 40 px by design (`apps/web/e2e/layout.spec.ts`), so "at least 44 px tall" holds only on a phone. The 0.2.4 regression was a link 3 px wide, which a height-only check would pass, so the live check also requires 200 px of width, as the e2e suite does.
9. **The pinned journey is checked on its transform step** (`?event=evt_demo_pinned_5550100_transform`): "value lost" is in the diff table, which only that URL renders, and the journey header with `Likely cause: phone` is on the same page.
10. **How `EXPECTED_VERSION` is found.** `git describe --tags --abbrev=0 --match 'v[0-9]*' --exclude '*-*'`, after `git fetch --tags --force --quiet origin` with `GIT_DEPTH: 0`. The spec's `--match 'v*'` would pick a pre-release tag, which publishes no images, so the demo never runs one; and GitLab's shallow clone need not hold the tag (`upgrade-test` fetches tags for the same reason). It is written `${EXPECTED_VERSION:-...}` so a manual play can override it, which the red run in Task 8 needs. The footer check also requires the summary's title to name that version for both `Web` and `API`, so a partial upgrade fails.
11. **`publish-python` stays manual on a Python pre-release tag.** The Python tag pattern accepts `a`, `b` and `rc` pre-releases, and `docs/OPERATIONS.md` documents rehearsing on TestPyPI with such a tag. If `publish-python` ran on its own, every rehearsal would upload to the real PyPI. It runs on its own for a final version, as the spec says, and is manual with its failure allowed on a pre-release.
12. **The ntfy post cannot be proven from the branch.** `NTFY_TOPIC_URL` is protected, so a merge request pipeline never sees it, and the spec's "once with a wrong `EXPECTED_VERSION` to see it fail and post to ntfy" from the branch can only show the warning path. Task 8 proves the red run and the warning on the branch, and leaves the post itself to Jorge after the merge (Step 8.9).
13. **`github-release` was already automatic.** It never had `when: manual`; the test holds it automatic.
14. **No CHANGELOG entry.** Nothing that ships changes; this is the project's own CI.

```ts
import { existsSync, readdirSync } from "node:fs";
import { describe, expect, it } from "vitest";
import { parse } from "yaml";
import { read, root } from "./docs-helpers.js";

/**
 * Which jobs a pipeline creates, read from .gitlab-ci.yml by evaluating its
 * rules the way GitLab does (ADR-073, issue #10).
 *
 * Every push to a branch with an open merge request used to make two
 * pipelines, and the merge request's held one job, so a green merge request
 * pipeline said almost nothing. The browser and stack jobs were manual
 * everywhere, so a 3 px journeys link and a broken smoke check both merged.
 * These tests hold the layout that replaced it: one pipeline per push, the
 * branch's work in the merge request pipeline, e2e, demo and upgrade-test
 * automatic and blocking where their code changed, and a release that
 * publishes on its own and deploys by hand.
 *
 * The reader below supports the rule syntax this file uses (`if` with `==`,
 * `!=`, `=~`, `!~`, `&&`, `||`, parentheses and `null`; `changes` as a list or
 * `paths`) and throws on anything else, so new syntax cannot be misread
 * silently.
 */

interface Rule {
  if?: string;
  changes?: string[] | { paths: string[]; compare_to?: string };
  when?: string;
  allow_failure?: boolean;
}

type Need = string | { job: string; optional?: boolean };

interface Job {
  rules?: Rule[];
  when?: string;
  allow_failure?: boolean;
  needs?: Need[];
  script?: string[];
  after_script?: string[];
  variables?: Record<string, string | number>;
}

const ci = parse(read(".gitlab-ci.yml"), { merge: true }) as Record<string, unknown> & {
  workflow?: { rules: Rule[] };
};
const KEYWORDS = new Set(["default", "variables", "stages", "workflow", "include"]);
const jobs = Object.fromEntries(
  Object.entries(ci).filter(([name]) => !KEYWORDS.has(name) && !name.startsWith("."))
) as Record<string, Job>;

const job = (name: string): Job => {
  const found = jobs[name];
  if (found === undefined) throw new Error(`.gitlab-ci.yml has no ${name} job`);
  return found;
};

/** One pipeline GitLab could create. */
interface Pipeline {
  source: "push" | "merge_request_event" | "schedule" | "web";
  /** The branch pushed, or the merge request's source branch. */
  branch?: string;
  tag?: string;
  openMergeRequest?: boolean;
  /**
   * The changed files `changes:` compares: the merge request's diff, or the
   * push's. Absent where GitLab has nothing to compare and `changes:` is
   * always true (tags, schedules, runs from the UI).
   */
  files?: readonly string[];
  variables?: Record<string, string>;
}

// GITHUB_TOKEN is set in the project, so the mirror jobs exist.
const PROJECT_VARIABLES = { GITHUB_TOKEN: "configured" };

const feature = (files: readonly string[]): Pipeline => ({
  source: "push",
  branch: "feature",
  files
});
const mergeRequest = (files: readonly string[]): Pipeline => ({
  source: "merge_request_event",
  branch: "feature",
  openMergeRequest: true,
  files
});
const main = (files: readonly string[]): Pipeline => ({ source: "push", branch: "main", files });
const schedule = (variables: Record<string, string> = {}): Pipeline => ({
  source: "schedule",
  branch: "main",
  variables
});
const tag = (name: string): Pipeline => ({ source: "push", tag: name });

function variablesOf(pipeline: Pipeline): Record<string, string> {
  const variables: Record<string, string> = {
    ...PROJECT_VARIABLES,
    CI_DEFAULT_BRANCH: "main",
    CI_PIPELINE_SOURCE: pipeline.source,
    ...pipeline.variables
  };
  if (pipeline.tag !== undefined) variables["CI_COMMIT_TAG"] = pipeline.tag;
  // A merge request pipeline has no CI_COMMIT_BRANCH; it has the MR's variables instead.
  else if (pipeline.source !== "merge_request_event" && pipeline.branch !== undefined) {
    variables["CI_COMMIT_BRANCH"] = pipeline.branch;
  }
  if (pipeline.openMergeRequest === true) {
    variables["CI_OPEN_MERGE_REQUESTS"] = "jojithedev/wayscribe!11";
  }
  return variables;
}

/** A `rules:if` expression, evaluated as GitLab does. */
function evaluate(expression: string, variables: Record<string, string>): boolean {
  const tokens =
    expression.match(
      /\$\w+|"[^"]*"|'[^']*'|\/(?:\\.|[^/\\])+\/[a-z]*|&&|\|\||[=!]=|[=!]~|[()]|\S+/g
    ) ?? [];
  let at = 0;
  const next = (): string => {
    const token = tokens[at++];
    if (token === undefined) throw new Error(`unexpected end of ${expression}`);
    return token;
  };
  const operand = (token: string): string | undefined => {
    if (token.startsWith("$")) return variables[token.slice(1)];
    if (token === "null") return undefined;
    if (/^["']/.test(token)) return token.slice(1, -1);
    throw new Error(`unsupported operand ${token} in ${expression}`);
  };
  const atom = (): boolean => {
    const token = next();
    if (token === "(") {
      const inner = either();
      if (next() !== ")") throw new Error(`unbalanced parentheses in ${expression}`);
      return inner;
    }
    const operator = tokens[at];
    if (operator === "==" || operator === "!=") {
      at++;
      return (operand(token) === operand(next())) === (operator === "==");
    }
    if (operator === "=~" || operator === "!~") {
      at++;
      const literal = /^\/(.*)\/([a-z]*)$/.exec(next());
      if (literal === null) throw new Error(`expected a regex in ${expression}`);
      const subject = operand(token);
      const matched =
        subject !== undefined && new RegExp(literal[1] ?? "", literal[2] ?? "").test(subject);
      return matched === (operator === "=~");
    }
    const value = operand(token);
    return value !== undefined && value !== "";
  };
  const both = (): boolean => {
    let result = atom();
    while (tokens[at] === "&&") {
      at++;
      const right = atom();
      result = result && right;
    }
    return result;
  };
  const either = (): boolean => {
    let result = both();
    while (tokens[at] === "||") {
      at++;
      const right = both();
      result = result || right;
    }
    return result;
  };
  const result = either();
  if (at !== tokens.length) {
    throw new Error(`cannot read ${tokens.slice(at).join(" ")} in ${expression}`);
  }
  return result;
}

/** A `changes:` pattern, as GitLab's fnmatch reads it: `*` stays within a directory. */
function globToRegExp(glob: string): RegExp {
  let source = "";
  for (let index = 0; index < glob.length; index++) {
    const character = glob.charAt(index);
    if (character === "*" && glob.charAt(index + 1) === "*") {
      if (glob.charAt(index + 2) === "/") {
        source += "(?:.*/)?";
        index += 2;
      } else {
        source += ".*";
        index += 1;
      }
    } else if (character === "*") source += "[^/]*";
    else if (character === "?") source += "[^/]";
    else source += character.replace(/[.+^${}()|[\]\\]/g, "\\$&");
  }
  return new RegExp(`^${source}$`);
}

function changed(changes: Rule["changes"], pipeline: Pipeline): boolean {
  if (changes === undefined || pipeline.files === undefined) return true;
  const patterns = Array.isArray(changes) ? changes : changes.paths;
  return pipeline.files.some((file) =>
    patterns.some((pattern) => globToRegExp(pattern).test(file))
  );
}

interface Outcome {
  when: string;
  allowFailure: boolean;
}
const NEVER: Outcome = { when: "never", allowFailure: false };

/** Whether `name` is in the pipeline, and how. */
function outcome(name: string, pipeline: Pipeline): Outcome {
  const found = job(name);
  if (found.rules === undefined) {
    // No rules is GitLab's `only: [branches, tags]`, which leaves merge request pipelines out.
    if (pipeline.source === "merge_request_event") return NEVER;
    const when = found.when ?? "on_success";
    return { when, allowFailure: found.allow_failure ?? when === "manual" };
  }
  const variables = variablesOf(pipeline);
  for (const rule of found.rules) {
    if (rule.if !== undefined && !evaluate(rule.if, variables)) continue;
    if (!changed(rule.changes, pipeline)) continue;
    const when = rule.when ?? found.when ?? "on_success";
    if (when === "never") return NEVER;
    // A manual job may fail by default, unless `when: manual` is a rule's.
    const allowFailure =
      rule.allow_failure ?? found.allow_failure ?? (when === "manual" && rule.when === undefined);
    return { when, allowFailure };
  }
  return NEVER;
}

function created(pipeline: Pipeline): boolean {
  const rules = ci.workflow?.rules;
  if (rules !== undefined) {
    const variables = variablesOf(pipeline);
    const first = rules.find(
      (rule) =>
        (rule.if === undefined || evaluate(rule.if, variables)) && changed(rule.changes, pipeline)
    );
    if (first === undefined || first.when === "never") return false;
  }
  return Object.keys(jobs).some((name) => outcome(name, pipeline).when !== "never");
}

const needNames = (name: string): string[] =>

/** Every workspace package `starts` depends on, directly or not, as directories. */
function workspaceDependencies(starts: readonly string[]): string[] {
  const directories = new Map<string, string>();
  for (const parent of ["apps", "packages"]) {
    for (const entry of readdirSync(`${root}${parent}`)) {
      const manifest = `${parent}/${entry}/package.json`;
      if (!existsSync(`${root}${manifest}`)) continue;
      directories.set((JSON.parse(read(manifest)) as { name: string }).name, `${parent}/${entry}`);
    }
  }
  const found = new Set<string>();
  const queue = [...starts];
  for (const directory of queue) {
    const manifest = JSON.parse(read(`${directory}/package.json`)) as {
      dependencies?: Record<string, string>;
      devDependencies?: Record<string, string>;
    };
    for (const [name, range] of Object.entries({
      ...manifest.dependencies,
      ...manifest.devDependencies
    })) {
      if (!range.startsWith("workspace:")) continue;
      const dependency = directories.get(name);
      if (dependency === undefined) throw new Error(`${directory} needs ${name}, not found`);
      if (!found.has(dependency)) {
        found.add(dependency);
        queue.push(dependency);
      }
    }
  }
  return [...found].sort();
}
```

```js
/* global AbortSignal */
// The live-demo CI job's after_script (.gitlab-ci.yml, ADR-073): when the
// check failed, post one line with the pipeline's URL to NTFY_TOPIC_URL.
//
// It never fails the job a second time. GitLab ignores an after_script's exit
// status anyway, and a missing topic (NTFY_TOPIC_URL is protected, so a merge
// request pipeline has none) or an unreachable ntfy prints a warning and exits
// 0. The topic URL is never printed.
//
//   CI_JOB_STATUS=failed NTFY_TOPIC_URL=https://ntfy.sh/<topic> node scripts/live-demo-alert.mjs

import { pathToFileURL } from "node:url";

/** How long the post may take before it is given up. */
export const POST_TIMEOUT_MS = 10_000;

/**
 * @param {{
 *   env: Record<string, string | undefined>;
 *   post: (url: string, body: string) => Promise<{ ok: boolean; status: number }>;
 *   log: (line: string) => void;
 * }} io
 * @returns {Promise<"not-failed" | "no-topic" | "sent" | "send-failed">}
 */
export async function alertOnFailure({ env, post, log }) {
  if (env.CI_JOB_STATUS !== "failed") return "not-failed";
  const topic = env.NTFY_TOPIC_URL;
  if (topic === undefined || topic === "") {
    log(
      "live-demo: warning: NTFY_TOPIC_URL is not set (it reaches main and v* pipelines only), so no alert was sent"
    );
    return "no-topic";
  }
  const ref = env.CI_COMMIT_REF_NAME ?? "an unknown ref";
  const pipeline = env.CI_PIPELINE_URL ?? "no pipeline URL";
  try {
    const response = await post(topic, `Wayscribe live-demo check failed on ${ref}: ${pipeline}`);
    if (!response.ok) {
      log(`live-demo: warning: ntfy answered ${String(response.status)}, so no alert was sent`);
      return "send-failed";
    }
    log("live-demo: alert sent");
    return "sent";
  } catch (error) {
    const reason = error instanceof Error ? error.name : "an error";
    log(`live-demo: warning: ntfy could not be reached (${reason}), so no alert was sent`);
    return "send-failed";
  }
}

/** POSTs `body` as plain text, giving up after POST_TIMEOUT_MS. */
export async function postText(url, body) {
  const response = await fetch(url, {
    method: "POST",
    headers: { "content-type": "text/plain; charset=utf-8", title: "Wayscribe live demo" },
    body,
    signal: AbortSignal.timeout(POST_TIMEOUT_MS)
  });
  return { ok: response.ok, status: response.status };
}

if (process.argv[1] !== undefined && import.meta.url === pathToFileURL(process.argv[1]).href) {
  await alertOnFailure({ env: process.env, post: postText, log: (line) => console.log(line) });
}
```

```markdown
**Status:** Accepted, 2026-10-19. Follows issue #10 and
`docs/superpowers/specs/2026-10-19-ci-layout-design.md`. Changes where `e2e`, `demo` and
`upgrade-test` run (ADR-041 recorded them as manual), how pipelines are chosen, and the
release flow ADR-069 describes for the demo.

**Context.** Four gaps each let something through. `e2e`, `demo` and `upgrade-test` were
manual on merge request and main pipelines, so the 3 px journeys link on phones (live until
0.2.4) and a broken smoke check pattern merged because nobody played them. Every push to a
branch with an open merge request made two pipelines, and the merge request's held one job,
so a green merge request pipeline said almost nothing; on 2026-10-19 MR !10 merged on that

until the manual `publish-images` was played. And nothing in GitLab looked at
demo.wayscribe.dev from outside: the smoke check reads HTML and cannot see layout or the
released version.

**Decision.**

1. One pipeline per push. A `workflow: rules` block runs the merge request pipeline while one
   is open and the branch pipeline otherwise; `main`, tags, schedules and pipelines started
   from the UI run as before. Every job's rules were reviewed against it: a job without
   rules never runs in a merge request pipeline, so the jobs that run everywhere say so, and
   the jobs that excluded merge requests because the branch pipeline covered them (`site`,
   `video`) no longer do.
2. `e2e`, `demo` and `upgrade-test` are path-scoped. On a merge request each runs on its own
   when its paths change and is manual otherwise, with its failure allowed so an unplayed job
   cannot block the merge. On `main` and on schedules all three always run. Where they run on
   their own they block. The reason they were manual still holds: a red pipeline on every
   push for a suite needing the whole stack trains people to ignore it. A suite that runs
   when its code changed is red when red means something.

   phone, the pinned journey's lost value and likely cause, and the release in the footer.

   holding that job alone) and after `deploy-demo` on a release tag. A failure fails the
   pipeline and posts one line to ntfy. `pnpm test:e2e` never reaches production.

   `publish-python` run on their own once their gates pass; `release-verify`, `upgrade-test`

   `demo-overlay`. `deploy-demo` stays manual and needs `publish-images` only.
```

```bash
dir="${TMPDIR:-/tmp}/ws-ci" && mkdir -p "${dir}"
cat > "${dir}/api-json.sh" <<'EOF'
#!/bin/sh
# api-json.sh <path> <js-expression over j>: prints the expression's value
# for the JSON at /projects/jojithedev%2Fwayscribe/<path>.
set -eu
glab api "projects/jojithedev%2Fwayscribe/$1" |
  node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const j=JSON.parse(s);console.log(eval(process.argv[1]))})' "$2"
EOF
cat > "${dir}/pipeline-for.sh" <<'EOF'
#!/bin/sh
# pipeline-for.sh <sha> <source> <deadline-seconds>: waits for GitLab to
# create the commit's pipeline from <source> (push, merge_request_event) and
# prints its id; prints every pipeline for the commit to stderr; exits 1 at
# the deadline.
set -eu
deadline=$(( $(date +%s) + $3 ))
while :; do
  all=$(sh "$(dirname "$0")/api-json.sh" "pipelines?sha=$1" 'j.map((p)=>p.id+" "+p.source+" "+p.status).join("\n")')
  id=$(printf '%s\n' "${all}" | awk -v source="$2" '$2 == source {print $1; exit}')
  if [ -n "${id}" ]; then printf '%s\n' "${all}" >&2; echo "${id}"; exit 0; fi
  if [ "$(date +%s)" -ge "${deadline}" ]; then echo "timeout: no $2 pipeline for $1" >&2; exit 1; fi
  sleep 15
done
EOF
cat > "${dir}/wait.sh" <<'EOF'
#!/bin/sh
# wait.sh <pipelines|jobs> <id> <deadline-seconds>: prints the final status
# (success, failed, canceled, skipped), or "timeout <status>" and exits 1.
set -eu
deadline=$(( $(date +%s) + $3 ))
while :; do
  status=$(sh "$(dirname "$0")/api-json.sh" "$1/$2" 'j.status')
  case "${status}" in
    success|failed|canceled|skipped) echo "${status}"; exit 0 ;;
  esac
  if [ "$(date +%s)" -ge "${deadline}" ]; then echo "timeout ${status}"; exit 1; fi
  sleep 30
done
EOF
cat > "${dir}/jobs.sh" <<'EOF'
#!/bin/sh
# jobs.sh <pipeline-id>: one line per job, "id status allow_failure name".
set -eu
sh "$(dirname "$0")/api-json.sh" "pipelines/$1/jobs?per_page=100" \
  'j.map((x)=>x.id+" "+x.status+" "+x.allow_failure+" "+x.name).join("\n")'
EOF
job_id() { sh "${dir}/jobs.sh" "$1" | awk -v name="$2" '$4 == name {print $1; exit}'; }
echo "helpers in ${dir}"
```
