## What it does

Search a customer, order or invoice ID, or any other identifier the record
answers to, and get that record's history in order, across every service that
touched it. Open a step and see what it received next to what it produced, field
by field.

## How it differs

<CardGrid>
  <Card title="Follows records, not requests" icon="magnifier">
    You search by a business ID. One record is a Salesforce ID in one service,
    an internal ID in another and a queue message ID in between; search any of
    them and you get the same journey. Tracing can find spans by attributes you
    add; Wayscribe makes aliases across services the primary navigation.
  </Card>
  <Card title="Shows the field that changed" icon="document">
    Each step records what it received and what it produced. The diff is
    structural, a path with its value before and after, so a renamed field and a
    lost value both show.
  </Card>
  <Card title="Replays a step against development" icon="random">
    Rerun a step's recorded input against a development destination on an
    allowlist, and compare the new result with the recorded one. Replay to
    production is not supported.
  </Card>
  <Card title="Runs on your own PostgreSQL" icon="database">
    PostgreSQL is the only required backing service. No Kafka, no
    Elasticsearch, no agent, no workflow engine to move your code onto. The SDK
    wraps the code you already have.
  </Card>
</CardGrid>

It is not a replacement for OpenTelemetry. When OpenTelemetry is present, the
SDK reads the active trace and span IDs onto each event, so you can move
between the two.

## Try it in a minute

You need Docker with Compose. Nothing else: no Node, no database, no account.

```bash
git clone https://gitlab.com/jojithedev/wayscribe.git && cd wayscribe
```

```bash
docker compose -f infrastructure/compose.yaml \
               -f infrastructure/compose.demo.yaml up --build
```

That builds the images and starts the API, the interface, PostgreSQL, a queue,
and four demo services with a broken integration to investigate. Measured on
2026-09-14 from a fresh clone on a laptop with no Docker layer cache, the build
took 38 seconds and the boot 12; the first run also downloads the base images.

Then start a journey:

```bash
curl -X POST http://localhost:3100/trigger
```

Open `http://localhost:3000`, sign in with the development admin token,
`replace-for-local-development-0000`, and search `0018Z00002ABC`. Set your own
token and encryption key before the stack holds anything real; the
[quick start](/docs/quick-start/#try-it) shows how.

## Instrument a service

The Node SDK, `@wayscribe/node`, has **no usable release on npm yet**. The
deprecated `0.0.1-placeholder.0` only reserves the name and contains no SDK.
Until the first release, pack it from a clone of the repository, commit the tarball to your application,
and install it by path:

```bash
pnpm install
pnpm --silent --filter @wayscribe/node run pack:release /path/to/your-app/vendor/
cd /path/to/your-app
npm install ./vendor/wayscribe-node-0.1.0.tgz
```

One recorder per process:

```typescript
return createRecorder({
  endpoint: process.env.WAYSCRIBE_URL ?? "http://localhost:8080",
  apiKey: process.env.WAYSCRIBE_API_KEY ?? "",
  serviceName,
  // Must be the environment the API key was issued for.
  environment: process.env.WAYSCRIBE_ENVIRONMENT ?? "development",
  // Leads carry personal data. Keep the fields, replace their values.
  redact: ["**.email", "**.phone"],
  // Prints `delivered_first`, or why nothing arrives. Off once it sends.
  logDiagnostics: process.env.NODE_ENV !== "production"
});
```

Then, in a webhook handler, a journey per record and a wrapper per step:

```typescript
// The entity is what someone will search for: the form provider's lead id.
const journey = recorder.startJourney({ entity: { type: "lead", id: leadId } });
journey.record({ operation: "received", name: "receive-lead-webhook", input: request.body });

let lead: Lead;
try {
  // Records the body going in and the lead coming out, and the diff between.
  lead = journey.transform("normalize-lead", request.body, () => parseLead(request.body));
} catch (error) {
  journey.fail("reject-malformed-lead", error);
  response.status(422).json({ error: "malformed lead" });
  return;
}
```

Both excerpts come from the
[Express, BullMQ and HubSpot recipe](/docs/recipes/express-bullmq-hubspot/),
whose code the repository type-checks against the SDK on every pipeline. The SDK
needs Node.js 22.12 or later and has no runtime dependencies.

## Trust

- **Self-hosted.** No account and no hosted service. Everything is kept in your
  own PostgreSQL, 15 or later.
- **No telemetry.** The running services send no telemetry and no analytics,
  and make no outbound connection other than the ones your configuration
  creates, such as replays to the development hosts you allow. This site has no
  analytics, no trackers and no cookies either.
- **Apache-2.0**, for every package, the SDK included.
- **Redaction by field name**, at any depth: in the SDK before a payload leaves
  your process, and again on the server before it is stored. A credential under
  a name no rule knows is warned about, not redacted. Entity identifiers and
  alias values are encrypted at rest; payloads are stored as plain `jsonb` after
  redaction.
- **A security review packet** for the engineer deciding on a pilot: data,
  authentication, deletion, supply chain and known gaps, each linked to its
  source. The pre-release security review it cites (2026-09-16) was done by an
  AI review agent at the maintainer's direction. It is not an independent audit,
  and no outside party has reviewed the code.
- **A 0.x preview.** No usable SDK release or release images are published
  yet. npm's deprecated placeholder reserves the package name only. Releases
  will be 0.x, where a minor release may change the API.
- **How it is built.** AI agents write most of the code; the maintainer makes
  the decisions, and each is recorded with its reasoning in the decision log.
